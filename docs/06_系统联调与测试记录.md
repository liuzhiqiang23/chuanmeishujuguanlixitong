## 1. 联调目标与链路

系统为「Vue 前端 → Spring Boot 后端 → Python 算法脚本」三层结构，本次联调要打通的链路有四条：

| 链路 | 前端页面 | 后端接口 | 算法/数据侧 |
| ---- | -------- | -------- | ----------- |
| ① 影片库浏览 | `/movie/list`、`/movie/detail` | `POST /api/movie/page`、`GET /api/movie/detail/{id}`、`GET /api/movie/stats` | MySQL `movie_analytics_db` 15 张新项目表 |
| ② 票房预测 | `/predict/index` | `POST /api/predict`、`POST /api/predict/logs` | `predict_api.py` + `best_model.joblib` + `feature_meta.json` |
| ③ 批量预测 / 算法对比 | `/predict/index`（批量页签）、`/predict/compare` | `POST /api/predict/batch`、`GET /api/predict/algo-compare` | 批处理调用同一推理脚本；对比数据读 `metrics.json` 与 `algo_comparison.png` |
| ④ 智能推荐 | `/recommend/UserList`、`/recommend/subject/edit` | `POST /api/recommend` | `recommend_api.py` 内容相似度矩阵（含磁盘缓存） |

统一调用约定：后端 `PythonRunner` 用 ProcessBuilder 逐参数传参（不经 shell），脚本 stdout **最后一行**必须是 JSON；成功 `{"ok":true,...}`，失败 `{"error":"原因"}`；超时（预测 20s / 推荐 30s / 批量 180s）自动 `destroyForcibly`。

## 4. 系统调试记录（联调中发现并修复的问题）

| # | 现象 | 根因 | 处理 |
| - | ---- | ---- | ---- |
| 1 | 后端启动报 `No qualifying bean of type 'java.lang.String'` | `PredictServiceImpl`/`RecommendServiceImpl` 用 `@AllArgsConstructor` + `@Value` 注入脚本路径，Spring 把 String 也当构造参数注入 | 改为显式构造器，只注入依赖 Bean |
| 2 | 所有走 `WebContext.getCurrentUser()` 的接口 500（首次暴露在 `/api/recommend`） | 管理端登录后 principal 是用户名字符串，旧代码直接强转 `UserDetails` 导致 ClassCastException | `instanceof` 分支兼容 `UserDetails` / `String`，匿名返回 null |
| 3 | `t_movie_cast` 导入 0 行 | 预处理产物中 cast/crew 为 **Python 字面量**（单引号），`json.loads` 解析失败返回空 | 先 `ast.literal_eval`，失败再回退 `json.loads` |
| 4 | 导入报 `DataError 1406: Data too long for column 'character_name'` | TMDB 角色名超出建表长度 | 统一 `_str(v, limit)` 截断后再入库 |
| 5 | 预算 2.37 亿的影片只预测出 328 万美元 | 未提供 vote_count 等字段时按 0 填充，被模型推到「零热度」角落 | 训练侧导出 `feature_meta.json` 的 `defaults`（各字段训练中位数）作为插补值；同一输入改为 3840 万 |
| 6 | 前端预测结果读不到值（一直为空） | 脚本返回 `log_revenue` 下划线，前端取 `logRevenue` | 统一为驼峰，脚本侧修正 |
| 7 | `feature_meta.json` 无法入库（被 .gitignore 忽略） | 父目录 `models/` 整体排除会阻断子文件反包含 | 改为 `models/*` + `!models/feature_meta.json` |
| 8 | 一键脚本报「'-' 不是内部或外部命令」 | `.cmd` 含 `chcp 65001` + LF 换行，cmd.exe 解析错乱 | 脚本改为纯 ASCII + CRLF |
| 9 | 重启脚本杀不掉旧进程，健康检查被**旧实例**应答 | PowerShell `Get-NetTCPConnection` 在该环境返回空 | 改用 `netstat -ano | findstr :8000` 取 PID（`tokens=5`） |
| 10 | 影片卡片大量「无海报」 | 本机网络对 `image.tmdb.org` 连接被重置（`themoviedb.org` 主站可达，仅图片 CDN 不通） | 环境问题，非代码缺陷：海报地址按 TMDB w300 规则拼装，网络可达时即正常；已在《用户手册》FAQ Q6 说明 |

## 5. 性能与一致性实测

| 指标 | 实测值 | 说明 |
| ---- | ------ | ---- |
| 单片预测（未命中缓存） | 约 3.7s | 含启动 Python 进程、加载模型与 34 列特征工程 |
| 单片预测（命中缓存） | 6–8ms | 后端按请求参数做 Redis 结果缓存（`predict:v2:`） |
| 批量预测 | 20 条约 2.8s | 一次起进程内按 200 行分批推理，摊薄启动开销后单条成本极低 |
| 推荐接口 | 0.06s | 相似度矩阵磁盘缓存命中（首次构建约 14.5s，缓存键含文件大小+mtime+版本号） |
| 算法对比页数据 | 0.01s | 读离线 `metrics.json`，不重训 |
| 训练/推理一致性 | **RMSE 0.3436、R² 0.9328、相关系数 0.9732、平均偏差 −0.0138** | `tools/verify_inference_consistency.py` 取 500 条训练样本回灌在线推理脚本对比（样本内） |

一致性校验的意义：在线推理与离线训练复用同一份 `feature_meta.json`（34 列特征、11 个主类型 one-hot、7 个国家 one-hot、训练中位数），回灌样本的预测值与真实 log10(票房) 几乎落在同一分布（平均偏差 −0.0138 ≈ 票房 3%），说明两端特征工程没有错位。

## 6. 遗留问题与结论

* 遗留（不阻塞）：TMDB 图片 CDN 在本机网络不可达，海报显示为占位符；提供网络时自动恢复。TMDB API key 与数据集原始包已按仓库规范做忽略处理。
* 遗留（设计如此）：站内评分表 `t_rating` 与评分用户表 `t_movie_user` 当前为 0 行（新项目未提供打分入口），因此推荐接口的「站内高分偏好加权」分支不会触发——前端文案与 `MovieMapper` 注释均已说明「数据不足时自动跳过」，验收项 12 已确认该分支可安全跳过而不报错。15 张新项目表中 13 张有数据（`t_movie` 1 万行、关系表最大 8.4 万行），满足「≥8 张表」的要求。
* 无阻塞性缺陷：17 项接口验收 + 4 个新增页面走查 + 回归项全部通过。
* 结论：**web 与算法联调完成，系统调试通过**，可进入第八步（一键启动脚本 + 用户手册）。
